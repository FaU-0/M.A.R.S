# Многопоточная расшифровка речи в M.A.R.S.: мини-отчёт

## Задача

Распараллелить расшифровку речи так, чтобы разные пары «врач + пациент» обрабатывались одновременно:
- на Python 3.14 без GIL — потоками;
- на Python с GIL — процессами.

Затем сравнить с прежним вариантом без параллельности.

## Что сделано

- **Выбор режима** (`shared/parallel.py`). Если GIL выключен (Python 3.14t, free-threaded), используются потоки, иначе — процессы. Решает не номер версии, а то, выключен ли GIL на самом деле после загрузки библиотек.
- **Сервис речи** (`speech/main.py`): пул исполнителей вместо одного куска за раз. Потоки работают с одной общей моделью Whisper, процессы — каждый со своей.
- **Очередь заданий** (`gateway`): куски разных пар уходят на расшифровку одновременно, куски одной пары — по порядку.
- **Python 3.14t** — режим по умолчанию: `python3 run_all.py`.

## Стенд и условия замера

| | |
|---|---|
| Компьютер | MacBook Pro 13", Intel Core i5 1,4 ГГц, 4 ядра (8 потоков), 8 ГБ RAM, без видеокарты |
| Модель | Whisper `small`, `int8`, на процессоре |
| Без параллельности | Python 3.12, 1 исполнитель (как было раньше) |
| С потоками | Python 3.14.10t без GIL, 2 исполнителя |
| Нагрузка | 1, 2, 4, 8 пар одновременно. Каждая сторона (врач и пациент) отправляет кусок 10 с настоящей русской речи раз в 10 с. Пары говорят 60 с, затем очередь дорабатывается до конца |
| Порог «работает нормально» | Текст готов не позже чем через 30 с после отправки куска (p95) |

Запускался только сервис расшифровки, остальная система не мешала. Скрипт: `loadtest/bench_transcribe_load.py`.

## Результаты

| Пар | Отставание текста p95: без параллельности | Отставание текста p95: с потоками | Кусков в минуту: без → с | Сбои | Текст совпадает с расшифровкой без нагрузки |
|---|---|---|---|---|---|
| 1 | 6,8 с | 5,9 с | 12,8 → 13,0 * | 0 | 100 % |
| 2 | **32,8 с ✗** | **17,9 с ✓** | 16,7 → 21,0 | 0 | 100 % |
| 4 | 118,6 с ✗ | 76,1 с ✗ | 16,2 → 21,8 | 0 | 100 % |
| 8 | 298,6 с ✗ | 200,3 с ✗ | 15,6 → 21,9 | 0 | 100 % |

\* На 1 паре скорость равна темпу речи: 12 кусков в минуту, исполнители простаивают.

Отдельный замер без нагрузки, на одних и тех же 25 кусках, 3 повтора:
- с потоками в **1,4 раза быстрее** (69 с против 97 с);
- доля ошибочных слов одинакова — **20,7 %** в обоих вариантах.

## Выводы

1. **Потоки удвоили число пар, которые расшифровываются вовремя: 2 вместо 1.** Без параллельности на 2 парах текст опаздывает на 33 с, с потоками — на 18 с.
2. **Скорость под нагрузкой выросла на 31–40 %:** около 22 кусков в минуту вместо 16–17. Отставание на 4–8 парах меньше примерно на треть.
3. **Качество и надёжность не пострадали:** ни одного сбоя, текст на 100 % совпадает с расшифровкой без нагрузки.
4. **С 4 пар не справляется ни один вариант:** речь идёт быстрее, чем 4 ядра успевают её расшифровывать. Потоки лучше используют то же железо, но не добавляют ядер. Рост дальше упирается в процессор.
5. **Что дальше:** компьютер с большим числом ядер (пары независимы, и потоки будут масштабироваться почти пропорционально), видеокарта для Whisper или более лёгкая модель.

**Итог:** многопоточность на Python 3.14 без GIL без потери качества удвоила число пар, расшифровываемых вовремя. Дальнейший рост ограничен числом ядер процессора.

## Ограничения замера

- На Python 3.14t нет сборки `onnxruntime`, поэтому отсечение тишины (VAD) там выключено. На результат это не повлияло: текст совпал на 100 %.
- Библиотека PyAV на 3.14t при загрузке включает GIL обратно. Поэтому расшифровка запускается с `PYTHON_GIL=0`, на нашу ответственность.
- Ступени нагрузки прогонялись по одному разу.

Подробный нагрузочный тест всей системы: `loadtest/REPORT.md`.
